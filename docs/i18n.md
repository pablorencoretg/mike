# Interface languages

The web app's interface is available in English and Spanish. English is the
source language; every other language is a dictionary with the same keys.

## Choosing the language

For each request the language is resolved in this order:

1. the viewer's choice in **Settings → Appearance → Language**, kept in the
   `mike_locale` cookie;
2. the deployment default, `MIKE_DEFAULT_LOCALE` (`en` or `es`), set on the
   frontend service (see `.env.example` and `docker-compose.yml`);
3. the browser's `Accept-Language` header;
4. English.

The root layout (`frontend/src/app/layout.tsx`) resolves it on the server, so
the first render, the `<html lang>` attribute and the page title are already
in the right language.

This setting covers the interface only. The language of the assistant's
answers is a separate setting under **Settings → Personalisation → Response
style**.

## Code layout

| Path | Purpose |
| --- | --- |
| `frontend/src/shared/i18n/locales.ts` | Supported locales and resolution rules |
| `frontend/src/shared/i18n/messages/en.ts` | English strings (source of truth) |
| `frontend/src/shared/i18n/messages/es.ts` | Spanish strings |
| `frontend/src/shared/i18n/translate.ts` | `createTranslator(locale)` and `{name}` interpolation |
| `frontend/src/shared/i18n/I18nContext.tsx` | `useT()` and `useI18n()` hooks |
| `frontend/src/app/components/i18n/I18nProvider.tsx` | Web provider; stores the choice |
| `frontend/src/app/lib/serverLocale.ts` | Request locale for server components |

## Translating a component

```tsx
import { useT } from "@/shared/i18n/I18nContext";

export function Example({ count }: { count: number }) {
    const t = useT();
    return <p>{t("example.selected", { count })}</p>;
}
```

1. Add the key to `messages/en.ts`, grouped by screen or feature.
2. Add the same key to `messages/es.ts`. TypeScript rejects a dictionary with
   a missing or extra key, and `t()` rejects an unknown key.
3. Keep every `{placeholder}` of the English string;
   `translate.test.ts` checks this.

Server components call `createTranslator(await getRequestLocale())` instead
of the hook. Without a provider (unit tests, isolated renders) `useT()`
returns English, so existing English assertions keep passing.

Components in `frontend/src/shared/ui/` are also compiled into the Word
add-in, which has no language provider yet. Pass translated text to them as
props (as `AuthDividerUI` takes `label`) rather than calling `useT()` inside.

## Spanish style

Informal "tú", neutral Latin American Spanish. Product names (Mike, Google,
SSO, Word) and established legal-operations terms such as *playbook* stay as
they are.

## Coverage

Not every screen is translated yet. A key missing from a locale falls back to
English, and an untranslated component simply shows its English text, so a
partially translated interface is always usable.
